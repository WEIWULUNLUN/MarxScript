# 小程序 ↔ CH582F 通信协议（v5）

ASCII 行协议，**每包以 `\n`(0x0A) 结尾**。小程序端实现在 `utils/protocol.js` + `utils/link.js`。

- 传输：BLE 自定义服务，写通道（小程序 → 板子）、Notify 通道（板子 → 小程序）
- **单包不写死**：连接后先协商 MTU（`wx.setBLEMTU` → `wx.getBLEMTU`，`writeType` 必须与实际写入方式一致），
  再用一条带空格填充的 `PING` **实测**真实可写长度（见第九节）。
  打字：**一包 10~17 条命令（110~187 字节）**，优先用无应答写；单条命令仍走 `_send` 逐条
- 一次 BLE 写里会拼进多条命令（每条自带 `\n`），靠行缓冲逐条解析
- 板子侧用 **行缓冲 + 超时丢弃**（收到 `\n` 才解析，超过 256 字节无 `\n` 清空）

## 〇、蓝牙广播与连接锁定

| 项 | 规则 |
|---|---|
| 广播名 | `MarxScript-XXXX`，`XXXX` = 芯片出厂 MAC 的 4 位十六进制（固定，终身不变） |
| 设备页排序 | 扫描结果里 `MarxScript` 前缀的全部置顶，组内按 RSSI 降序；其他名称保持发现顺序 |
| 单手机锁定 | **应用层令牌**：小程序连上后发 `BIND:<令牌>`，固件只认第一个令牌；令牌不符的手机可以连上，但发不出任何按键，并会被断开 |

> 为什么不用蓝牙地址：荣耀/鸿蒙等机器断连重连会上报**不同的随机静态地址**，
> 按地址锁定会把主人自己挡在门外（症状正是「首次能连、断连后再也连不上」）。
> 令牌存在手机本地存储（`kb_client_id`），与地址无关，重连多少次都一样。
> 解除锁定：断电重启，或按 RST 键（令牌只存 RAM）。

## 一、下行命令（小程序 → 板子）

| 命令 | 说明 | 板子应答 |
|---|---|---|
| `AUTH:<key>\n` | 鉴权，连接后小程序自动发一次 | `OK\n` 或 `FAIL\n` |
| `BIND:<id>\n` | 身份令牌（12~32 位十六进制），鉴权后立刻发 | `BOUND:NEW` / `BOUND:SAME` / `BOUND:OTHER` |
| `CAP\n` | 询问开发板能力：单包上限、队列深度、当前两个间隔 | `CAP:<maxWrite>:<queue>:<delay>:<gap>\n` |
| `SET:DELAY:<ms>\n` | **字内间隔**：Alt 与数字、数字与数字之间的延时，0~500 | `OK\n` |
| `SET:GAP:<ms>\n` | **字间间隔**：上一个字松开 Alt 到下一个字开始，0~500 | `OK\n` |
| `CODE:<dec>\n` | 输入一个字符，dec 为十进制数值 | 输入完成后回 `DONE\n` |
| `KEY:<mod>:<usage>\n` | 模拟一次按键（按下即抬起），见第七节 | `DONE\n` |
| `KD:<mod>:<usage>\n` | **按下并保持**（宏序列的原子动作） | 序列内不回，见第八节 |
| `KU:<mod>:<usage>\n` | **抬起**；`KU:0:0` = 把所有按住的键全部松开 | 序列内不回 |
| `W:<ms>\n` | **纯延时**，由固件 timer 计时，不受 BLE 往返影响 | 序列内不回 |
| `SEQ:BEGIN\n` / `SEQ:END\n` | 序列容器，整段只回一个 `DONE` | `OK` → 执行完 `DONE` |
| `STOP\n` | 终止：清空板内 FIFO、松开所有按键、立刻停止 Alt 输出 | `STOPPED\n` |
| `PING\n` | 心跳；也用作单包长度实测（见第九节） | `PONG\n` |
| `VER\n` | 查固件版本 | `VER:<tag>\n` |
| `MACRO:GET\n` | 读取全部宏 | 逐条 `MACRO:...`，最后 `OK\n` |
| `MACRO:SET:<i>:<T\|K>:<hex>\n` | 写第 i 个键（0 起）的宏 | `OK\n` |
| `MACRO:RESET\n` | 恢复板内默认宏 | `OK\n` |

执行类命令（`CODE` / `KEY` / `KD` / `KU` / `W` / `SEQ`）要求 **鉴权通过且绑定通过**，
否则回 `FAIL`。板子还没有主人时（刚上电、没人认领）允许直接执行。


错误统一回 `ERR:<msg>\n`，小程序会弹提示但不中断后续命令。

## 二、`CODE:<dec>` 的语义（核心）

Windows 的「Alt + 小键盘」规则：

- `dec` ≤ 255：按 ANSI/OEM 单字节解释 → **ASCII 直接透传**（`CODE:65` = `A`）
- `dec` > 255：按当前代码页（中文系统 CP936 = GBK）的双字节值解释 → `CODE:50403` = `你`

小程序发送的 `dec` 来源：

| 字符类型 | dec 计算 | 例子 |
|---|---|---|
| 可打印 ASCII | 就是字符码 | `A` → `CODE:65` |
| 汉字 / 中文标点 | `(lead << 8) \| trail`，GBK 机内码 | `你` = 0xC4E3 → `CODE:50403` |
| 换行 `\n` | 固定 13（CR） | 相当于按一下回车 |
| Tab | 9 | |
| 转不了的字 | 63（`?`），并已在发送前弹窗告知用户 | |

> 板子拿到 `dec` 后：`Alt` 按下 → 用**小键盘键码**依次敲十进制数字（`2` 用 `KC_KP_2`，不要用主键盘数字）→ 松开 `Alt` → 回 `DONE`。
> 三位/四位统一按十进制数字逐位敲，不要补零、不要转十六进制。`Alt+065` 与 `Alt+65` 在 Windows 上等价，但补零会让部分输入法误判，小程序默认不补零。

**DONE 的时机**：必须是「Alt 已松开、按键序列已全部发出」之后，建议再加 5~15ms 稳定延时再回。
早回 `DONE` 会导致下一条字符在 Windows 还没处理完上一个 Alt 码时到来 —— 这就是典型的"丢字/串字"。

## 三、上行通知（板子 → 小程序）

| 内容 | 说明 |
|---|---|
| `OK\n` | 通用成功 |
| `DONE\n` | 单个 `CODE` / `KEY` 执行完成（老格式，只回一个标记） |
| `DONE:<n>\n` | 同上，但带**本次连接内已完成的累计条数**（v38+，`n` 从 1 起） |
| `STOPPED\n` | `STOP` 已执行，FIFO 清空、按键已松开 |
| `FAIL\n` | 鉴权失败 / 命令拒绝 |
| `PONG\n` | 心跳应答 |
| `ERR:<msg>\n` | 错误详情，会以 toast 形式提示用户 |
| `VER:<tag>\n` | 固件版本号（`FW_BUILD_TAG`） |
| `MACRO:<i>:<T\|K>:<hex>\n` | 宏配置回报，`hex` 是 UTF-8 字节的十六进制 |
| `BOUND:NEW\n` | 令牌已登记（这台板子第一次被认领） |
| `BOUND:SAME\n` | 令牌与板上记录一致，放行 |
| `BOUND:OTHER\n` | 已被别的手机绑定：回完这行就断开 |
| `CAP:<maxWrite>:<queue>:<delay>:<gap>\n` | 能力上报，见第九节 |
| `INFO:<msg>\n` | 调试信息，小程序忽略（仅日志） |

`OK`/`DONE`/`STOPPED`/`PONG` 在小程序里都算「这一条已处理完」，是滑动窗口计数的来源。

**为什么 `DONE` 要带序号**：BLE 的 notify 没有确认，丢一条就是永久丢失。
老协议下小程序只能「数条数」——发 9 个字必须收到 9 条 `DONE`，少一条就永远等下去
（真机上的表现就是「8 个字正常、9 个字报 DONE 超时」）。带序号之后，中间丢 N 条不影响：
下一条一到序号直接跳到真实值，小程序按差值把进度补齐。
序号在链路建立时归零，只表示「本条连接内的相对值」，不需要持久化。

`MACRO` 的 `hex` 例：`CTRL+C` → `43 54 52 4C 2B 43` → `MACRO:3:K:4354524C2B43`；
文本「患者一般情况可」→ UTF-8 hex 后同格式，`T` 表示文本。

## 四、典型时序

```
小程序                          板子
  |-- createBLEConnection ------->|
  |-- 订阅 Notify --------------->|
  |-- AUTH:demo1234 ------------->|
  |<--------------------- OK -----|
  |-- SET:DELAY:30 -------------->|
  |<--------------------- OK -----|
  |-- CODE:50403 ---------------->|  Alt + 50403
  |<------------------- DONE -----|
  |-- CODE:47811 ---------------->|  Alt + 47811
  |<------------------- DONE -----|
  |-- KEY:1:6 ------------------->|  Ctrl+C（按下即抬起）
  |<------------------- DONE -----|
  |-- STOP ---------------------->|  用户点了「终止」
  |<----------------- STOPPED ----|
  |-- PING ---------------------->|  （空闲 20s 后）
  |<------------------- PONG -----|
```

## 五、给固件的几条硬要求

1. **UART/BLE 缓冲**：至少 64 字节行缓冲；解析不完整就等下一个包。
2. **不要在小程序写完立刻回 OK 再慢慢做事**：`CODE` 的回执必须是「真的输入完了」。
3. **`DONE` 必须真的到、真的准**：小程序已经不靠「数条数」判进度了（v38 起认 `DONE:<n>` 序号），
   但连续 1.5~3 秒没有**任何**新回执仍会判定「回执中断」并中止。所以：
   - notify 发出失败（`GATT_bm_alloc` 拿不到缓冲、`blePending`）要重试，不能静默丢弃；
   - 序号必须单调递增，链路重建时归零。
4. **鉴权失败必须回 `FAIL`**，不要静默不回，否则小程序会等 3.5s 超时。
5. **宏写 Flash** 建议先 `OK` 再擦写，写完掉电不丢；`MACRO:GET` 遍历 12 个键，每个不超过 20 字节（`MACRO:i:K:xx...` 会超 20 字节时小程序会自动切片，板子要按行拼接）。

## 六、想改协议怎么办

只改 `utils/protocol.js` 的 `CMD` 和 `parseLine`，`link.js` 不用动（它只认 `OK/DONE/STOPPED/FAIL/PONG/STAT/ERR` 等语义）。

## 七、`KEY:<mod>:<usage>` 的键值表

`mod` 是 HID 修饰键位图，可相加：

| 位 | 键 | 值 |
|---|---|---|
| bit0 | 左 Ctrl | `0x01` |
| bit1 | 左 Shift | `0x02` |
| bit2 | 左 Alt | `0x04` |
| bit3 | 左 Win | `0x08` |

> ⚠️ 踩过的坑：Alt 是 `0x04`，不是 `0x02`（`0x02` 是 Shift）。写错会表现为「按 Ctrl+C 出来的是 Shift+C」。

常用 usage（HID Usage ID，Keyboard/Keypad 页）：

| 键 | usage | 键 | usage |
|---|---|---|---|
| Enter | `0x28` | Esc | `0x29` |
| Backspace | `0x2a` | Tab | `0x2b` |
| Space | `0x2c` | CapsLock | `0x39` |
| A–Z | `0x04`~`0x1d` | 1–9 | `0x1e`~`0x26`，0 = `0x27` |
| 方向键 右/左/下/上 | `0x4f`/`0x50`/`0x51`/`0x52` | Delete | `0x4c` |
| F1–F12 | `0x3a`~`0x45` | 小键盘 1–9 / 0 | `0x59`~`0x61` / `0x62` |

例子：`KEY:1:6` = Ctrl+C；`KEY:4:43` = Alt+Tab；`KEY:0:63` = F6（注意是十进制，不是十六进制）。

板子收到后只做一件事：`hid_report(mod, usage)` → 等 1 个报文周期 → `hid_report(0, 0)` → 回 `DONE`。

## 八、宏序列（`SEQ` + `KD` / `KU` / `W`）

> 开源版小程序已移除宏页面与 `utils/macro.js`，本节仅说明固件仍支持的协议能力，供二次开发参考。

`KEY` 只能表达「按一下」，做不了「按住 A 再按 B」「连按三次回车」，也没法控制间隔。
所以宏改成**整段下发、板子自己跑**：

```
SEQ:BEGIN
KD:1:6         ← 按下 Ctrl+C（mod=1 把 Ctrl 挂在 C 上）
W:50           ← 等 50ms
KU:1:6         ← 抬起
W:50
KU:0:0         ← 兜底：全部抬起（小程序总是会自动加这一条）
SEQ:END
```

想做「按住 Ctrl 一段时间、中间连按几个键」，把修饰键写成独立步骤即可
（修饰键的 usage 是 `0xE0`~`0xE7`，固件会把它转成报文第 0 字节的修饰位）：

```
SEQ:BEGIN
KD:0:224       ← 按下左 Ctrl（224 = 0xE0）
W:100
KD:0:4         ← 按 A
W:50
KU:0:4
W:50
KD:0:5         ← 按 B
W:50
KU:0:5
W:50
KU:0:224       ← 松开左 Ctrl
W:50
KU:0:0
SEQ:END
```

| 修饰键 | usage | 修饰键 | usage |
|---|---|---|---|
| 左 Ctrl | `0xE0` (224) | 右 Ctrl | `0xE4` (228) |
| 左 Shift | `0xE1` (225) | 右 Shift | `0xE5` (229) |
| 左 Alt | `0xE2` (226) | 右 Alt | `0xE6` (230) |
| 左 Win | `0xE3` (227) | 右 Win | `0xE7` (231) |

要点：

| 项 | 规则 |
|---|---|
| 回执 | `SEQ:BEGIN` / `SEQ:END` 各回一个 `OK`；只有 `SEQ:END` 压入的结束标记执行完才回 **一个** `DONE`。序列内的步骤不回任何东西，否则 12 步刷 12 个回执 |
| 计时 | `W:<ms>` 由固件 timer 执行，精度几毫秒；**不要**靠小程序逐条发来实现间隔（每条约 20~40ms 抖动） |
| 按键状态 | 固件维护「当前按住的键集合」（修饰键位图 + 最多 6 个 usage），`KD` 加、`KU` 减，每次都发完整 8 字节报文。所以按下 A → 按下 B → 抬起 A 不会把 B 顶掉 |
| 队列 | 板内 FIFO 64 项（12 步宏约 30 项）。超了回 `ERR:QUEUE_FULL`，小程序会自动分批 |
| 中断 | 任何时候 `STOP` 都会清队 + 全部抬起，宏立刻停 |
| 重试 | 宏**不重试**：里面可能有非幂等的「按下」，重发会重复按键 |

内部完整版的小程序侧对应 `utils/macro.js`（开源版已移除，以下仅供二次开发参考）：

- `{ mod, usage, action:'down'|'up', delay }` 为一步
- `compile(macro)` 生成上面那段文本 + 估算总耗时（用于超时与卡片显示）
- `mode`：`once` 执行一次 / `hold` 按住时循环 / `anykey` 点击开始、任意处停止；
  循环发生在小程序侧（每轮一条完整宏），这样随时能 `STOP` 打断，固件不用做无限循环模式


## 九、单包长度：协商 + 实测 + 自动降档

「单包 20 字节」曾经是最大的性能瓶颈：一个中文字的 `CODE:50403\n` 就是 11 字节，
20 字节的包一次只能装一条，等于每个字都要一次 BLE 往返。

### 定长顺序

1. `wx.setBLEMTU(mtu)`，依次尝试 **185 → 128 → 100**（部分安卓 ROM 第一次会失败）；
2. `wx.getBLEMTU({ writeType })` 读回，`writeType` 必须与特征值实际属性一致
   （固有属性是 `write` 就传 `'write'`），传错会拿回 23 这种偏小值；
3. `CAP` 问开发板要单包上限（= FFE1 特征值长度 200）与队列深度；
4. **实测**：发 `PING` + 空格填充到 n 字节 + `\n`，回 `PONG` 说明这个长度
   真能写进去。固件解析会去掉行尾空格，所以填充不影响命令语义。

### v0.9.1 定案：包长由「写一次的代价」决定

**v0.8.0 的「逐条 11B」和 v0.9.0 的「打包 4 条」都不够。** 逐像素换算按键记录截图后，
真实节奏是这样的：

```
一包 4 字：打字爆发 280ms → 空白 500ms → 下一包，周期 800ms = 5 字/秒
```

板子确实在等数据，但它不是处理不过来 —— 是手机还没来得及把下一包写过去。

于是吞吐率有个干净公式：

```
吞吐 = 包内字数 / max(写一次的耗时, 包内字数 × 单字耗时)
```

写一次约 500ms（有应答写 + 手机端串行队列），包内 4 字只要 280ms 就敲完了，
所以卡在写那一侧。**把包做大就是把「等写」摊到更多字上**。

仿真（`tools/sim_ack.js` 场景 7-8，写 500ms / 快速档 90ms 字 / 39 字）：

| 方案 | 总耗时 | 固件空转 | 速度 |
|---|---|---|---|
| 包 4 条 + 有应答写 | 5555ms | 1389ms | 7.0 字/秒 |
| 包 6 条 + 有应答写 | 4164ms | 0ms | 9.4 字/秒 |
| 包 4 条 + 无应答写 | 3674ms | 0ms | **10.6 字/秒** |
| 包 6 条 + 无应答写 | 3676ms | 0ms | **10.6 字/秒** |

无应答写（`writeNoResponse`）直接把那 500ms 的往返抹掉，吞吐随即由打字速度决定。
它没有失败反馈，所以：连接时的 `PING` 探测会先验证它到底送不送得到
（送不到就换回有应答写、在同一个包长上重试，不白砍包长）；
发送中若出现「打字中断」，也会自动退回有应答写并记住。

### v0.10.0：闸门看「空位」，包长顶到特征值上限

前两版的闸门都错在「用回执来节流」：

| 版本 | 闸门 | 结果 |
|---|---|---|
| v0.9.1 | 在途满 3 包 → 等最老那包的 DONE | 写之前先陪跑前两包的字，5 字/秒 |
| v0.9.2 | 已压 48 字以上 → 等回执降到 48 | 只解决断粮，没解决「写的成本」 |
| **v0.10.0** | **先腾出够一整包的空位，再写** | 包长 17 条，39 字只写 3 次 |

现在的闸门只有一条：

```
空位 = 48 - 已压未敲的字数
空位 < 这一包的条数 → 等回执腾位              否则 → 直接写
```

为什么必须按「一整包」算空位：固件 `kbd_tx_push()` 队列满时是**静默丢**
（返回 0，不回错），手机侧完全感知不到 —— 只要包长大于剩余空位，就会丢字。
v0.9.2 的 `已压 > 48 才等` 在包长顶到十几条时正好踩这个坑。

### 包长按「写一次的耗时」自动定

```
包内字数 × 单字耗时 ≥ 写一次的耗时 × 2.4
```

| 实测 `写 均` | 单字 66ms 时算出的包长 | 包内打字时长 |
|---|---|---|
| 500ms（有应答写） | 18 → 顶到上限 **17 条（187B）** | 1.1 秒 |
| 15ms（无应答写生效） | 6 条（66B） | 0.4 秒 |

上限 17 条不是 MTU 决定的，而是固件 FFE1 特征值长度 200 字节（留 8B 余量 → 192B）。
第一次发送用 10 条，之后每次按**上一次实测的 `写 均`** 重算。

仿真（`tools/sim_ack.js` 场景 6~8，写 500ms、快速档、39 字）：

| 包长 | 总耗时 | 固件空转 | 速度 |
|---|---|---|---|
| 6 条 | 3933ms | **371ms** | 9.9 字/秒 |
| 10 条 | 3561ms | 0 | 11.0 字/秒 |
| **17 条** | **3569ms** | **0** | 10.9 字/秒 |
| 17 条 + 写 800ms | 3851ms | 0 | 10.1 字/秒 |

「固件空转」= 板子手上没活的时间，就是用户听到的停顿。17 条把它压到 0。

- **行对齐**：一包永远是整数条 `CODE:...\n`，绝不切在命令中间。
- **写失败降包长**，记住在 `kb_pack_memo_v1`；无应答写丢数据记住在 `kb_wtype_memo`。两者都不重发。
- 页面诊断行：`包N｜交接 …｜周期 …｜写 均X 最大Yms｜回执 均X 最大Yms`。
  **`回执 均` 就是固件真实的打字节奏**：稳定 70~80ms 说明键盘侧满速，
  冒出 400ms+ 才是键盘侧真的停了。

### 真正的物理上限：USB 帧数（v39 固件）

这一条比 BLE 侧重要得多。EP1 是中断 IN 端点，`bInterval` 决定每帧最快多久出去一次。

- v38 及以前：`bInterval = 10ms`，且每敲**一位数字发两帧**（「Alt+数字」按下 →
  「Alt」松开）。一个汉字 5 位 = 10 帧 + 1 帧松 Alt = **11 帧 = 110ms 硬底**，
  也就是最快 9 字/秒，而且 `delay` 被固件强制下限 10ms。
- v39 起：`bInterval = 2ms`，并且**一位数字只发一帧** —— HID 报文是「当前按下的键
  集合」快照，`[Alt + 0]` 本身就表达了「5 松开了、0 按着」，主机自己做差分。
  一个汉字 = 5 帧 + 1 帧松 Alt = **6 帧**，`delay` 下限降到 4ms。

于是每字耗时变成 `5×delay + 20 + gap`：

| 档位 | delay/gap | 每字 | 速度 |
|---|---|---|---|
| 稳妥 | 34 / 45 | 235ms | 4.3 字/秒 |
| 标准 | 22 / 22 | 152ms | 6.6 字/秒 |
| 快速 | 12 / 10 | 90ms | 11.1 字/秒 |
| 极速 | 6 / 4 | 54ms | 18.5 字/秒 |

`delay` 不能低于 4ms：低于两个轮询周期时，上一帧还没被主机取走就被下一帧盖掉，
表现为少一位数字。固件里也做了兜底（小于 4 按 4 执行）。

### 教训：一位一帧可以，但**重复位必须补一帧松开**

v39 把「一位数字两帧」改成「一位一帧」，靠主机自己做快照差分。这对**相邻两位不同**
的情况完全正确（这也是为什么大部分字打得对），但相邻两位**相同**时两帧内容一字不差，
主机会认为「这个键一直按着没动」，那一位数字就凭空消失：

| 字 | 码值 | 主机实际收到 | 结果 |
|---|---|---|---|
| 情 | 51177 | 517 | 无效码 → 整个字消失 |
| 重 | 55000 | 50 | Alt+50 → 打出个 `2` |
| ， | 41900 | 4190 | 无效码 → 标点消失 |

现场那段 39 字里，凡是码值带相邻重复数字的字全丢（情/清/精/尚/饮/便/重/变），
一个不多一个不少 —— 这就是定位到它的依据。

v40 的修法只在重复位多花一帧：先发「只按 Alt」把上一位真正松开，下一拍再按下。
6 帧/字的常态不变，重复位变 7 帧。

护栏：`tools/sim_ack.js` 场景 5 做了**报文级**回归 —— 用一个「只在报文变化时才认按下」
的假主机去重放每个字的帧序列，直接报出「打歪 N/39 字」。

### v42：`STAT` —— 回执丢了也能知道真实进度

```
下行  STAT
上行  STAT:<已完成累计序号>:<队列里还没敲的条数>
```

BLE 的 notify 是**无确认**的。长文本（858 字要跑 46 秒）中途偶发丢一串 `DONE`
完全正常，而小程序此前只能看到「3 秒没有新回执」，无法区分两种情况：

| 真相 | 以前的处理 | 后果 |
|---|---|---|
| 固件还在正常敲，只是回执没到 | 报「打字中断」，让用户重发 | 重发 → 前面的字重复一遍 |
| 固件真的卡死 | 同样报「打字中断」 | 正确的 |

有了 `STAT`（v42 固件），卡住时问一句就知道：

- 序号变大了 → 回执只是丢了，直接对账补齐，继续发，**用户全程无感**
- 序号没变、`queued > 0` → 它正在敲，再等等
- 连续两次问不出任何进展 → 才报错

小程序侧实现：`_waitAck` 里静默 1.2 秒（`probeAfter`）就发一次 `STAT`（5 字节，
不参与批量流水线），最多问 2 次；报错门槛仍是 3 秒（`stall`）。

仿真（`tools/sim_ack.js` 场景 11）：连着丢 30 条回执，固件照常敲 —— 39 字仍然
完整送达，多花 1.3 秒；场景 12（连 `STAT` 都不回）正确报错。

### 水位下限是 2 包，不是 1

1 包在途 = 每发一包都要等这一包的 `DONE` 才继续。此时**只要丢一条回执，流水线
就永久停住** —— 没有新命令发出，也就不会有新 `DONE` 来补序号。现场那两次
「858 字卡在 683 / 610」都发生在「在途 1 包」时（是更早一次失败降级留下的）。

而且 1 包没有任何速度收益：写往返早就被敲字时间盖住了。所以 `_fallbackPipe()`
和水位记忆（`kb_win_memo_v5`）的下限都是 **2**。

### 打包下的失败语义

- **写失败立即停止，绝不重发**（重发会让同一批字打两遍，见下方「重复字」教训）
- 中断时自动发 `STOP` 清掉固件队列残留，避免重发时旧字混进新内容
- 错误文案给出「已输入 x/N 字」+「已发 k 包：44+44B」，x 之后的内容由用户重发

### 教训：一次「每批写两次」

v0.7.0 加时间线埋点时，`sendText` 里同时存在两行 `await ble.writeText(batch)`，
每批命令被写两遍。接收端表现是成对重复（「患者一般患者一般情况可，情况可，」），
随后队列积压、3 秒无回执报错，再触发水位降级 —— 用户感知成「每 4 字停半秒」。
**这个 bug 存在期间所有「打包失败」的结论都不可信**，包括「8 字可以 9 字必挂」
和「66B 零执行零回执」—— 它们都是双写把固件队列和回执序号搞乱的结果。

护栏：`tools/sim_ack.js` 增加「不重不漏」校验，比对固件收到的 `CODE` 序列与原文编码，
重复或错序立即报 `!! 重复发送`。

## v0.11.1：长文发到中途中断的三个真因

现场：858 字卡在 683 / 610，后来稳定复现在 **500~600 字**。
手机已设常亮，与熄屏无关（熄屏防护只是额外保险，见 `utils/screen.js`）。

### 真因一：`ERR:QUEUE_FULL` 被当成致命错误（最可能）

固件队列 64 条，满了 `kbd_tx_push()` 返回 0，`do_code()` 回 `ERR:QUEUE_FULL`。
小程序以前把它和 `BAD_CODE` 同级处理：`_bulk.err` 一设，发送循环下一轮就抛
「发送中断」，**整段作废**。

但它真正的含义只有一条：**这一条命令没进队列，这个字打不出来**。
链路完全正常，固件照常敲前面的，后面的字也完全能继续发。

现在收到它就做三件事，一个都不中止：

| 动作 | 原因 |
|---|---|
| `lost++` | 如实记录少了几个字，收尾时告诉用户 |
| `penalty += 8`，水位收缩 | 说明「已发-已回执」低估了真实队列，后面别接着撞同一堵墙 |
| 继续发 | 剩下的字跟这次拒收没有任何关系 |

**两个走过弯路、必须记住的坑：**

- 不能 `acked++` 补进度：被拒的命令不占 `s_ackSeq`，补了就永久偏移，
  最后 acked 到顶而固件还差 N 条没敲。
- 不能 `total--`：total 变小而 `d` 还在涨，中途就越过新 total 被当成"已完成"，
  发送提前收尾、后面的字被 `STOP` 清掉。

正确关系：本轮固件最终只完成 `total - lost` 条，`d` 最终也等于这个数。
所以判据、进度分母、在途计算全部统一用 `total - lost`。
**在途还要再减一次 lost**：`inflight = sent - lost - acked` ——
被拒的命令不占队列，不减它就会等一个固件永远达不到的 acked（死锁）。

### 真因二：回执序号的基准偏移

`d = (seq - base) & 0xffff`，base 取自「最后一次收到的 DONE」。
上一轮长文尾部若丢了十几条回执，base 就永久偏小，误差一轮一轮累积。

旧代码用 `d > total + 8` 判定「固件重启、序号归零」。基准偏移只差十几，
**长文正好能撞到这条线**：一撞就把 base 重置成本轮 seq、acked 归零，
之后 d 从 0 重新爬，永远追不到 target → 卡到超时 → 报「打字中断」。
短文本轮 total 小，反而不容易撞上 —— 这就是它专挑长文的原因。

两处修：

1. 判据改成 `d > 0x8000`。真正的序号归零 d 是六万级（`65536 - base`），
   基准偏移再多也只有几十，两者差了一个数量级，不会再混。
2. 发送开始前先发一条 `STAT`，用固件回报的真实序号当 base。
   主动查询不受丢回执影响，从源头消掉误差累积。问不到就退回旧值，不会更差。

### 真因三：PONG 混进回执流

`ACK_TYPES` 含 `PONG`（单条发送要认它）。批量发送期间若有一条心跳的 PONG
赶到，它会掉进 `if (this._bulk)` 分支：既不匹配 DONE、也没人 resolve 心跳的
pending —— 于是被当成「敲完一个字」把 acked++，同时心跳 1.5 秒超时、
missed++，两次就判「设备无响应」直接断开。

现在 PONG 在 `_onLine` 里先交给心跳等待者，然后立刻 `return`，
批量分支再加一道 `p.type !== 'PONG'` 的闸。

### 熄屏防护（额外保险，不是修复手段）

`utils/screen.js`：`setKeepScreenOn` 的引用计数封装。
`sendText` 持 `'send'`（开源版只有这一个持有者；内部完整版另有宏循环的 `'macro'` / `'macroLoop'`），
最后持有者释放时才真正交还系统；每 20 秒重设一次，防部分 ROM 丢状态；
断连、页面卸载、发送异常都会释放，不做延时关闭。

### 回归

新增两个场景（`tools/sim_ack.js`）：

- 场景 13：第一轮尾部丢 10 条回执，第二轮不能被误判成「序号归零」
- 场景 14：固件队列频繁满（`ERR:QUEUE_FULL`），必须继续而不是中止
  （假固件新增 `queueMax` 模型，拒收时回 `ERR:QUEUE_FULL`）

场景 14 的结果是「成功 28/39，拒收 11 字，已跳过」——
在队列只有 12 条的极端条件下仍然发完，只是少了几个字并如实报告。

## v0.11.2：长文中断的真因 —— 在途账目被「幽灵条数」撑爆

前提结论：**与熄屏无关**（现场手机已设常亮，照样断），熄屏防护只是保险。

### 为什么总是 500~600 字

BLE 的写是**无确认**语义。GATT 写返回成功，只代表数据交给了协议栈，
不代表进了固件。链路层丢包、写被合并、固件那头刚好重启，都会让某条
`CODE:` 命令**凭空消失**：它不会产生 DONE，也不会回 `ERR`。

小程序侧的「在途」是算出来的：

```
在途 = 已发 - 已敲完
```

幽灵条数只增不减，这个值就一路虚高。闸门认为「固件队列永远满」，
于是一直等一个永远不会到的 acked，几秒后抛「打字中断」。
**发得越久攒得越多**，所以报错位置总落在长文的同一段，而短文从不复现。

短文本轮 total 小，闸门还没被撑爆就已经发完了 —— 这就是它专挑长文的原因。

### 修法：用 STAT 做三方对账

固件答 STAT 那一刻，它已经按行序处理完此前所有命令，所以：

```
已发 = 已敲完（seq） + 队列里还压着（queued） + 消失的
```

消失的 = `sent - lost - acked - queued`。当场记进 `lost`，
账目立刻对齐，剩下的字继续发：不中断、不重发、不重复打字。

`_reconcileByStat()` 要求**同一个数连看两次**才记账：固件正在敲的那条
已经从队列出队、但还没算进 `seq`，单次观测会把它误判成消失；
它一个字的时间（~70ms）就会变成 done，所以第二次探测必然归零 ——
而真正丢掉的字不会。

### 第二道保险：卡住不等于坏了

`_waitAckResilient()` 包在 `_waitAck` 外面。卡住时先问 STAT：

| STAT 的回答 | 处理 |
|---|---|
| 序号变大了 | 回执只是丢了，进度补齐，继续 |
| 队列还有货 | 它正在敲，继续等（不记失败） |
| 账目对得出差异 | 丢字，记账跳过，继续 |
| 问不到 / 完全没进展 | 3 轮、最多 45 秒，才把错误抛给用户 |

以前是「3 秒没回执就整段作废」，用户只能重发，而重发会让前面已经
打出去的字再打一遍。现在只要固件还在动，就绝不打断用户。

### 回归

新增场景 15（`tools/sim_ack.js`，假固件新增 `swallowEvery` 模型）：
每 4 条静默吞 1 条，39 字里丢掉 9 个 —— 必须一路发完并如实报告，
而不是在第 30 个字上抛「打字中断」。

结果：`成功 30/39（5.0s），跳过 9 字，内容一致`。

同时把场景 14 的顺序校验也修干净了（被拒收/被吞的命令从期望序列里剪掉，
不再误报「第 13 条起不符」）。

## v0.11.3 + 固件 v43：通知通道停摆 —— 用「读」拿回真相

### 截图给出的决定性证据

现场报错（1014 字长文，3 次复现 684 / 692 / 699）：

```
已输入 692/1014 字 · 每包 6 条 · 在途 2 包 · 已发 123 包（738 字）
```

**「已发」减「已输入」每次都停在 45~48**，而固件队列软上限正是 48。
这说明：手机侧只是不再往里写，账面上压在固件里的量已经到顶。
固件到底在敲、还是停了，手机**看不见** —— 因为：

- `DONE:<seq>` 走 notify；
- `STAT:<seq>:<queued>` 的回包也走 notify。

通知通道一旦整段停摆，两条路一起断，手机侧只能超时报「打字中断」，
而桌面上字可能还在继续出。这不是「固件卡死」，而是**手机瞎了**。

安卓上这种行为是真实存在的：小程序连续几十秒、每秒十几条地接收通知，
`onBLECharacteristicValueChange` 的回调可能整段不再触发。

### 修法：加一条「读」通道（固件 v43 + 小程序 0.11.3）

固件每敲完一个字，把 `S:<已敲完>:<队列剩余>` 写进 FFE2 的值里
（`SIMPLEPROFILE_CHAR2_LEN = 20`，只改属性值，不触发 notify）。

小程序卡住时 `_queryStat()` **先读、读不到再问 STAT**：

| 手段 | 语义 | 通知断掉时 |
|---|---|---|
| notify（DONE / STAT） | 对端推，丢了不知道 | 全断 |
| **ATT read（FFE2）** | 手机拉，对端必须应答 | **照样读得到** |

读到之后的三种情况：

- 序号在涨 → 只是回执丢了：`_bulkSeq()` 先对账再返回，进度按真实值补齐，继续发；
- `queued > 0` → 固件还在敲，别打断用户；
- 序号冻住 + 队列也不动 → 这才是真死机，3 轮后如实报错。

**两个必须记住的坑：**

1. 读到的序号**必须先对账再返回**（`_bulkSeq(r.seq)`）。通知断了的时候
   没有 DONE 会替我们做这件事，漏了这一步，`acked` 停在旧值，紧接着的
   三方对账就会把「还在敲的字」全算成丢失（仿真里表现为「跳过 20 字」）。
2. 靠读兜底时要把探活间隔从 1.2s 收到 250ms（`readHits > 1`），
   否则闸门每 1.2 秒才放行一批，吞吐从 11.8 掉到 4.7 字/秒。

### 为什么「真死机」还能报错

ATT read 由协议栈应答，固件应用层挂了也读得到 —— 但读到的是**最后一次
写入的值**，序号和队列长度都冻住。所以判据看的是「读回来的数还在不在动」，
而不是「读得到读不到」。

### 回归

场景 16（新增）：通知通道完全停摆，`{ noNotify: true }`。
结果 `成功 39/39（3.3s，11.7 字/秒），内容一致`，全程无报错。

场景 12 改成「固件真的停住（`stopAfter`）」，仍然按预期报错 ——
两种情况现在能截然分开，这正是本次修复的核心价值。

## v0.11.4：只剩最后一条也报错 / 中途停十几秒

**固件不用重刷**，这一版只改小程序，继续用 v43。

### 现场

1014 字长文：

- 中途两次停顿，每次十几秒，之后能自己继续；
- 结尾弹「发送中断：已输入 **1013/1014**（已发 1014），3.0 秒无新进展」。
- 弹窗里 `66+66+…` 刷了十几行（169 包全拼出来了），把有效信息淹了。

用户原话「好像只差一点了」是准确的：**1014 条全部写完，固件敲完 1013 字**，
只差最后一条回执（或那条命令被链路吞了）。

### 真因：报错门槛把「自愈」本身变成了停顿

旧版 `_waitAck` 的链路是：

```
静默 1.2s → 探活（最多 4 次）→ 3s stall 抛错 → _waitAckResilient 兜 3 轮
```

- 通知一断，**4 次探活用完就必然抛错**，外层再走一轮又是 3 秒 ——
  用户看到的「停十几秒又继续」，就是自愈在空转，不是链路恢复得慢；
- 收尾时最后一条永远等不到，进度差 1，三轮后整段作废。
  可 1013 个字已经打进文档了，弹「发送中断」只会让人整段重发，
  把 1013 个字再敲一遍。

`_waitAckResilient` 还有两个放大延迟的 bug：`bestAck` 初值 -1（第一次接住
错误就误判成「有进展」），以及 `moved` 判定时 `_queryStat` 已经把 acked
推高、`beforeAck` 记录的却是推高后的值 → 有进展也不 continue，白等一轮。

### 修法一：只看「进度还在不在动」

`_waitAck` 重写成单循环：

| 项 | 旧 | 新 |
|---|---|---|
| 静默多久问一次 | 1.2s | **300ms**（一次 ATT read 仅 30~60ms） |
| 探活次数上限 | 4 次，用完必抛错 | **不限**（通知断了全靠 read 推进，限次数=制造停顿） |
| 报错条件 | 3s 没回执 | **连续 12 秒序号不涨、账目无差异、问也问不到** |
| 外层自愈 | 3 轮 × 12s | **再确认一次**，无进展立刻上抛 |

进度一动（回执补齐或对账记账）就重置死线，所以只要固件还在敲，**永不报错**。
真死机 / 拔线仍在 12 秒左右如实报错（场景 12 保持按预期失败）。

探活无进展时按 1.5 倍退避到 700ms，避免 12 秒里发 40 次 read 挤占链路；
一有进展立刻回到 300ms。靠 read 兜底时（`readHits > 1`）压到 **150ms** ——
此时 read 是唯一的放行节拍，300ms 一次会让吞吐掉一半。

### 修法二：尾部宽容收尾 `_trySettle()`

全部命令已写完、只差 1~2 条、且固件队列里剩的不超过差额时，
**同一个序号连看两次、间隔 > 3 个字的时间**（排除「正在敲最后一条」），
就把差额如实记进 `lost` 并判定完成：

- 不重发、不重复打字；
- 弹窗改成「已输入 1013 字，跳过 1 字（通常在结尾）」，
  并提醒**不要整段重发**；
- 不掩盖真故障：中途闸门等待时（`sent < total`）不适用，
  差额 > 2 或队列里还压着一堆货时也不适用。

`_reconcileByStat()` 同时加了「两次观测至少隔 120ms」的时间门槛，
防止两次探活挤在同一瞬间，把「固件正在敲的那条」误记成丢字。

### 修法三：报错信息能用了

- 169 包的 `66+66+…` 改成「已发 169 包，末包 66B（末 6 包 …）」；
- 追加「状态回读 N 次 / 跳过 N 字」——下次再出问题，
  一眼能分清是 read 通道没通，还是账目对不上。

## v0.11.5：真机读通道从未生效（截图 console 抓到）+ IDE 自动化接入

**固件不用重刷**（继续 v43）。这一版只改小程序。

### 决定性证据

开发者工具真机调试 console：

```
[KBD] ready mtu=247 chunk=668 ...
[notice] {"type":"ANNOUN","message":"S:1804:0"}
```

`S:1804:0` 是固件写进 FFE2 的**可读状态**，它出现在通知回调里 ——
说明 ATT read 的应答确实到了手机，但被 `parseLine` 当成未知行报了 notice，
而 `readStatus()` 自己什么也没拿到。

### 根因：微信 readBLECharacteristicValue 的返回值不在 success 里

官方文档明确：**读取到的值要在 `onBLECharacteristicValueChange` 回调里取**，
`success` 回调不含 `value`。v0.11.3 写的 `util.bufferToStr(res.value)` 恒为
`undefined` → 正则永不匹配 → `readStatus()` 每次 reject → `_queryStat()`
一路退回 `STAT\n` + 等 notify 回包 —— 而 notify 正是会停摆的那条通道。

**所以 v43 加的「读兜底」在真机上等于没接**，之前所有"长文修复"都只靠
notify 在撑。这也解释了为什么改了几轮仍会在长文末尾出错。

仿真之所以全绿，是假 wx 桩写成了 `o.success({ value })` —— 桩本身就不符合
真实 API，属于"假绿"。已一并修正。

### 修法

1. `ble.readStatus()` 改为订阅回调取值；`success` 里的 `res.value` 只作兼容。
2. `bindGlobalListeners` 把 `S:<seq>:<queued>` 分流到**私有 `stat` 事件**，
   不再 emit 到 `data`。
   - 原因：notify 与 read 共用同一个微信回调，若 `S:` 混进通知流，
     `link._onLine` 会把它当成固件主动上报的 STAT，提前 resolve
     `_statWaiter`、改 `_ackSeq`，长文账目立刻错乱（仿真场景 14 当场复现）。
   - `parseLine` 仍保留 `S:` 分支作防御，但正常路径走私有通道。
3. 仿真桩改成真实语义：`success({})` 不带 value，值经
   `onBLECharacteristicValueChange` 回调到；补 20 字节 \0 对齐固件。
4. `[KBD] ready` 日志追加 `stat=可读/不可用`，下次从 console 一眼确认通道。
5. `state` 初始化补 `statChar`，`snapshot()` 一并导出。

### 回归

仿真桩改成真实 API 后，场景 14（队列满）曾立刻回归失败（私有通道方案前），
修正后 20 个场景**全部通过**，含：通知全程停摆 234/234、尾部吞 1 条命令
不报错、真死机按预期报错、内容不重不漏。
